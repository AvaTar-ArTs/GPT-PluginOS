Pattern library

Beyond “primary + fallback.”

Advanced routing can use specialists, ensembles, shadows, canaries, Pareto frontiers, circuit breakers, provenance rules, and project-specific constraints.

🎯

Specialist-first routing

Choose the provider strongest at the exact capability instead of crowning one platform king of everything.

🪞

Shadow providers

Run a secondary provider for evaluation without exposing its result to the production workflow. Learn without risking production.

🐤

Canary routing

Send a small slice of eligible work to a new provider and compare quality, latency, cost, and failure patterns before promotion.

🧱

Privacy zones

Local-only, private-cloud, approved-remote, and public-data zones can alter which providers are even eligible.

🧯

Circuit breakers

Repeated failures, latency spikes, stale auth, or degraded output quality can temporarily demote a provider automatically.

📐

Pareto routing

Preserve multiple non-dominated choices when no provider simultaneously wins quality, cost, latency, privacy, and provenance.

Benchmark engine

Never ask “which provider is best?” again.

Ask which provider is best for a capability, policy context, and workload. Store the evidence as versioned observations.

Learning router

Let outcomes become routing evidence.

Human approvals, retries, rejected outputs, benchmark wins, and successful production runs can become evidence without turning the system into opaque autopilot.

observation:
  capability: design.product.audit
  provider: product-design
  outcome: accepted
  human_score: 0.93
  latency_ms: 4210
  project: creator-camp
  use_for_ranking: true
Advanced principle: PluginOS should make the system more explainable as it gets more capable. Every clever route needs an answer to “why this provider, under which policy, using what evidence, and what would have happened if it failed?”
